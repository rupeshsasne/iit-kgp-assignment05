The job

AeroVelo Logistics Global has a small pile of approved documents: policies, a supplier procedure, an incident SOP, a bill of materials, a governance matrix, and so on. People currently open those files one by one. The assignment is a notebook that lets someone ask a question and get an answer taken from those files, with the file names that supported it.

That pattern is retrieval-augmented generation, RAG. A search step finds the passages that might contain the answer. A language model then writes the answer from those passages, rather than from whatever it memorised in training. If the files do not contain the fact, the assistant is supposed to say so.

10 files→ clean text→ chunks→ MiniLM vectors→ Chroma→ 4 chunks→ Llama 3.2→ answer + sources

The notebook is worth 100 marks. Setup and imports are not graded. The graded work is the table above.

Answer similarity and retrieval similarity are similarity scores. They are not an accuracy percentage, and a high score is not proof the sentence is factually grounded. Topics, in the order the notebook needs them

A document object

LangChain's Document is two fields: page_content (the text) and metadata (a small dictionary). Retrieval later returns these objects, so the file name has to live in metadata or we cannot show a source. Category is the parent folder, because that is how the dataset groups the business function.

Markdown versus PDF

A Markdown file is already text. A PDF is a drawing of text. PdfReader pulls the characters back out, page by page. That extract is lossy: line breaks move, and the governance PDF comes back much shorter than its Markdown twin. We still index both, because the brief says to load every Markdown and PDF file.

Cleaning

The files contain trailing spaces (Markdown's two-space line break) and, in the PDF header, runs of spaces between fields. Cleaning turns line endings into \n, squeezes spaces and tabs on each line, strips the edges, and collapses three or more blank lines to one blank line. The word tokens before and after this pass are the same. Only the spacing changes. Meaning stays put.

Length

Document length here is the number of characters in page_content after cleaning. Average, maximum, and minimum describe the collection before we cut it into chunks. They are not word counts.

Stopwords and word frequency

A stopword is a function word such as "the" or "of". Counting those mostly tells you that English has articles. NLTK's English stopword list is removed, tokens are alphabetic words longer than one letter, and a Counter ranks what remains. The most common words describe the corpus. The least common count is 1: hundreds of words appear once, so "least frequent" is a tie, not a single special word.

TF-IDF

TF-IDF is a weight for each word in each document. Term frequency is how often the word appears in that file. Inverse document frequency lowers words that appear in many of the ten files, because those words do not distinguish one policy from another. A word that is common in one file and rare in the others keeps a high weight. After this step each document is a long list of numbers, one per vocabulary word, with zeros where the word never appears.

Cosine similarity

Cosine similarity is the angle between two of those lists. It ignores which file is longer and asks whether the same words carry the weight. A score of 1 is the same mix of important words. A score of 0 is no overlap in those weighted words. The diagonal of the matrix is 1 because every file matches itself. We only rank pairs of different files.

TF-IDF cosine can only see shared words. It cannot tell that "staff member" and "employee" are related. That limit is why the later retrieval step uses embeddings instead of this matrix.

Chunks and overlap

A whole policy is too coarse for a question about one rule. RecursiveCharacterTextSplitter cuts page_content into pieces of about 800 characters, and each piece repeats 120 characters from the previous piece. The overlap exists so a sentence that sits on a boundary is fully inside at least one chunk. Metadata is copied onto every chunk, or the source file is lost at retrieval time. Embeddings, and why they are not TF-IDF

all-MiniLM-L6-v2 is a small sentence-embedding model. It maps a chunk of text to a vector of a few hundred numbers such that chunks with similar meaning land near each other, even when they do not share the same keywords. TF-IDF in section 1.3 is an analysis of the whole documents. Embeddings in section 2 are the index we actually search. No device string is set. The library picks CPU, MPS, or CUDA.

A vector database

Chroma stores those vectors and, given a query vector, returns the nearest chunks. The collection name is logistics_rag and it is persistent, so a later run can reopen it instead of embedding the corpus again. The count of stored vectors should match the number of chunks.

The RAG chain

A retriever asks Chroma for 4 chunks. Those chunks are formatted into one context string. A prompt tells the model to answer from that context. init_chat_model("llama3.2:3b", model_provider="ollama", temperature=0) calls the local model. Temperature 0 asks for the least random wording the model will produce. The answer function also prints the source file names from the retrieved metadata.

Evaluation

Five questions need reference answers you can point at in a loaded file. For each question the notebook records two scores. Answer similarity is the embedding cosine between the generated answer and the reference answer. Retrieval similarity is the highest embedding cosine between the reference answer and any retrieved chunk. Then one extra question whose fact is absent from the collection, to see whether the assistant invents it. The conclusion cites the run's numbers, one limit, and the runtime: local Ollama llama3.2:3b at temperature 0 with MiniLM-L6-v2.
