Documents, PDF text, and cleaning

How a file on disk becomes a Document, why the governance PDF is a different object from the Markdown, and what the whitespace pass is allowed to change.

The unit the rest of the notebook holds

LangChain's Document is a small object with two fields. page_content is a string, the text we will split, embed, and show to the model. metadata is a dictionary that rides along and is not embedded. Retrieval returns documents, not bare strings. If the file name is only in a local variable that went out of scope, the answer function cannot print a source. That is the entire reason metadata exists in this assignment.

The brief names four keys. We use exactly these:

KeyValueWhy it has to survive chunking
file_nameSOP-COM-015_Regulatory_Breach_Report.mdThis is what we print next to an answer.
categorythe parent folder, such as complianceThe dataset is grouped by business function. The folder is that label.
file_typemd or pdfSo a later check can tell an extract from the original Markdown.
sourcethe pathSo a person can open the file that was retrieved.

Category is path.parent.name, not a hand-written map. The folder names already are the categories in the brief: compliance, finance, governance, hr, legal, operations, pdfs, supply_chain.

Finding the files

Path.rglob walks every nested folder. The filter keeps regular files whose suffix is .md or .pdf, case-insensitive. Sorted order makes the first document stable: the compliance SOP, because "compliance" sorts before "finance". There are 10 files. Nine are Markdown. One is the PDF of the regional governance matrix, which also exists as Markdown under governance/. Both are loaded. The brief says every Markdown and every PDF, and dropping the PDF because a twin exists would be a choice the brief did not offer.

Markdown is text. A PDF is not.

A Markdown file is opened as UTF-8 and the string is the document. A PDF is a sequence of drawing instructions that usually include the text. PdfReader walks the pages and calls extract_text on each. We join those page strings with newlines. If a page has no extractable text, that page contributes an empty string rather than crashing.

Extraction is lossy. Columns, headers, and line breaks are reconstructed heuristically. On this corpus you can see the damage in the lengths. The governance Markdown is about 4,968 characters after the whitespace pass. The PDF extract of the same matrix is 1,394 characters, and it is the shortest document we have. The PDF is still indexed, because a question might be answered from the lines that did survive, and because the assignment includes the pdfs folder. When TF-IDF later compares them, do not expect the PDF row to match the Markdown row at cosine 1. They are not the same string.

What cleaning is allowed to do

The files are already well formed. The mess is small and mechanical. Markdown uses two trailing spaces as a hard line break, so several header lines end in " ". The PDF header separates fields with runs of spaces: Document ID: RGM-2026 Version: 1.4. There are no tabs and no Windows \r\n in this particular download. The cleaner still handles \r\n and \r, because the notebook is supposed to run on Windows too.

The function does four things, in order:

  1. Turn any \r\n or \r into \n.
  2. On each line, replace runs of spaces and tabs with a single space, then strip the ends.
  3. Join the lines back with \n.
  4. Collapse three or more newlines into two, and strip the whole string.

It does not delete punctuation, lower-case the text, or remove stopwords. Those choices belong to the analysis cells, where they are visible. Cleaning rewrites page_content in place and does not touch metadata.

The check that this was safe: tokenise before and after. Across all ten files the tokens are identical. Only the character length moves, and only by the spaces we removed. The compliance SOP goes from 2,991 raw characters to 2,980. The length cell then reports the collection after this pass: average 4073.2, maximum 5599 (EMEA remote-work policy), minimum 1394 (the PDF).

Why length is in characters

The brief says document length, and the chunk size later is specified in characters (800), not tokens. Using len(page_content) makes the length cell and the chunker speak the same unit. A word count would also be a statistic. It would not tell you whether 800 characters is a small slice or almost the whole file. Here every file is longer than 800 characters, so every file will be split. The PDF, at 1,394 characters, becomes about two chunks. The EMEA policy, at 5,599, becomes many.

The inspect cell prints metadata, length, and the first 400 characters of docs[0]. That is a smoke test. If the PDF extractor had returned an empty string, or if category were missing, you would see it before any plot or matrix.
