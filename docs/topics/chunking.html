Chunking and overlap

Whole documents are the wrong unit for a question

The length cell already measured the folder. The shortest text is 1,394 characters. The longest is 5,599. A question such as "what is the reporting window for a critical breach?" needs one row of one table inside the compliance SOP, not the purpose statement, the appendix, and the version history. If we embedded each file as a single vector, that vector would be an average of every topic in the file. The breach-window sentence would be diluted by the rest of the SOP, and the model would be handed thousands of characters of context for a one-line fact.

Chunking cuts page_content into pieces small enough that one piece can be "about" one rule. The brief fixes the knife: 800 characters, with an overlap of 120 characters. Those numbers are not a suggestion. The notebook is graded against them.

Characters, not tokens

800 characters is roughly 120 to 160 English words, depending on the policy's table formatting. It is not 800 tokens. A token for Llama is often a short piece of a word, and MiniLM has its own tokeniser with a maximum length. We still cut on characters because that is the unit in the brief and the unit RecursiveCharacterTextSplitter uses when you pass chunk_size without a custom length function. The embedding model will tokenise each chunk again later. If a chunk's token count exceeds MiniLM's window, the model truncates. At 800 characters that is unlikely for this corpus. We do not retune the size to chase the model's window.

What "recursive" splits on

The splitter tries to break on paragraph boundaries first, then newlines, then spaces, and only then on raw characters. The order matters. A cut on a blank line keeps a section together. A cut in the middle of a word is the last resort, used only when a single line is itself longer than 800 characters, which a markdown table row might be.

Overlap means the next chunk starts 120 characters before the previous chunk ended. Take a toy line, with chunk size 20 and overlap 5, so the arithmetic fits on a page:

abcdefghijklmnopqrstuvwxyz

The first piece is abcdefghijklmnopqrst (20 characters). The next piece starts at index 20 - 5 = 15, so it begins with pqrst and continues. The shared pqrst is the overlap. If a sentence had ended at the boundary, both chunks would still contain its tail or its head. Without overlap, a fact that straddles the cut is in neither chunk intact, and retrieval can miss it.

On our settings the step is 800 - 120 = 680 characters of new text per chunk, with 120 repeated. The EMEA policy at 5,599 characters therefore becomes more than one chunk. The PDF at 1,394 becomes about two. The exact count depends on where the separators fall, so the notebook should print len(chunks) rather than a hand estimate.

Metadata has to be copied

Each chunk is its own Document. Its page_content is the slice. Its metadata must still carry file_name, category, file_type, and source from the parent. RecursiveCharacterTextSplitter.split_documents does that copy if you pass the document list. Building chunks from bare strings and forgetting the dictionary is the failure mode that makes every answer unsourced.

The splitter may also add its own keys, such as a start index, if you ask it to. We do not need extra keys for the grade. We do need the four we already stored.

What to look at when the rest of the section exists

  • The chunk count is greater than 10, because every file is longer than 800 characters.
  • A sample chunk's text is a readable slice of a policy, not a single word and not an entire file.
  • That sample's metadata still names the file it came from.
  • Neighbouring chunks from the same file share a run of characters about 120 long.
